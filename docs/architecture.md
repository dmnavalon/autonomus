# Architecture — Autonomus Software Factory Agent

## Overview

Autonomus is a GitHub-first, multi-agent pipeline that turns a natural-language Telegram
message into a Pull Request with a passing Vercel Preview and Playwright suite. The factory
is **never** allowed to merge to `main`, deploy to production, or touch secrets / billing.

```
Telegram ─▶ Vercel Function (webhook) ─▶ GitHub Issue (job, label state:received)
                                                │
                                                ▼
                              GitHub Actions: orchestrator.yml
                                                │
   ┌────────────────────────────────────────────┼─────────────────────────────────────────┐
   │                                            ▼                                          │
   │  Coordinator → Recepcionista → Clasificador → Planificador → Arquitecto → Router      │
   │                                            │                                          │
   │  ─→ Programador (branch factory/<n> + commits + PR) ─→ wait Vercel Preview            │
   │                                            │                                          │
   │  ─→ QA Planner ─→ Playwright (artifacts) ─→ Analista de Logs                          │
   │                                            │                                          │
   │  ─→ Reparador (loop ≤5) ─→ Verificador Final ─→ Telegram notify                       │
   └────────────────────────────────────────────┼──────────────────────────────────────────┘
                                                │
                                  GitHub: Issue comments, labels, PR, artifacts
```

## Source of truth = GitHub

| Concern | Where it lives |
|---|---|
| Job (request from user) | GitHub Issue in `dmnavalon/autonomus` |
| State machine | Issue labels (`state:*`, `type:*`, `repair:N`) |
| Per-agent decisions | Issue comments (compact JSON code blocks) |
| Code | Branch `factory/<n>` + Pull Request |
| Build / test logs | GitHub Actions artifacts (raw + Playwright trace) |
| Agent instructions | `agents/<n>/instructions.md` (versioned) |
| Flows by request type | `flows/*.md` (versioned) |
| Shared system prompt | `prompts/shared/system.md` (cacheable) |
| Allowed users | `registry/users.json` (versioned) |
| Known apps | `registry/apps.json` (versioned) |

No Supabase in MVP. If we need cross-job aggregation later, evaluate Postgres on Vercel
Marketplace — but only if a real metric requires it.

## Token efficiency (principio rector)

The system is engineered to minimize LLM tokens. Concrete mechanisms:

1. **Per-agent hard caps** (input + output) checked before each LLM call.
2. **Per-job hard cap** of 80k input + 15k output tokens, ≤ $2 USD. Alarm at 70%, abort at 100%.
3. **Prompt caching**. Every call sends the stable prefix
   `prompts/shared/system.md` + `agents/<n>/instructions.md` first → cache hits across all
   jobs and agents.
4. **Diffs only**. Programmer ↔ Reviewer ↔ Repairer pass `git diff --unified=3`, not files.
5. **Logs as artifacts**. Analyst sees only the last ~80 lines + grep for `error|fail|exception`.
6. **Cheap model by default**. Strong tier (Opus / GPT-5) only for code generation and repair.
7. **Escalation by failure**. Cheap → mid → strong only when schema validation fails twice.
8. **Telemetry per call**: `{agent, model, input_tokens, output_tokens, cached_tokens, cost_usd}`
   accumulated and posted as the final Issue comment.
9. **Determinism**: `temperature=0` for classification/checklists, `0.2` for code. No `n>1`.
10. **No reasoning mode** unless Reparador attempt ≥ 3.

## State machine

```
state:received
  → state:classifying       (Recepcionista + Clasificador)
  → state:planning          (Planificador + Arquitecto)
  → state:coding            (Router + Programador)
  → state:pr-created
  → state:waiting-preview
  → state:preview-ready
  → state:qa-planning       (QA Planner)
  → state:qa-running        (Playwright on Vercel Preview)
  ├─ ok → state:auto-approved → state:human-review-required (notify Telegram)
  └─ fail → state:qa-failed
            → state:repairing (label repair:N, N≤5)
            → state:retesting → loop to qa-running
            └─ N=5 → state:failed-needs-human (notify Telegram)
```

## Agents

Each agent is a `.ts` file in `packages/orchestrator/src/agents/`. It loads its instructions
from `agents/<n>/instructions.md`, calls the LLM via Vercel AI Gateway, validates output
against a Zod schema, posts a comment on the Issue, and transitions the label.

See `prompts/shared/json-schemas.md` for output schemas.

## Repos generated by the factory

For `software_nuevo`, the factory creates a new GitHub repo `dmnavalon/<slug>` from the
template `templates/nextjs-vercel-app/` and registers it in `registry/apps.json`. Each app
gets its own Vercel project. The factory itself never deploys those apps; Vercel's Git
integration handles previews on every branch push.

## Security model

- Webhook authentication: `X-Telegram-Bot-Api-Secret-Token` verified against
  `TELEGRAM_WEBHOOK_SECRET`.
- Authorization: `chat.id` must be in `registry/users.json`.
- GitHub PAT (`GH_AUTOMATION_TOKEN`): scopes `repo, workflow` only — no `admin`.
- Vercel token: read deployments + create previews only, no production deploys.
- Hardcoded forbidden ops in `packages/orchestrator/src/safety.ts` (regex blocklist).
- Secret detection on every agent output before commenting / committing.
- Branch protection on `main` (configured in repo settings, documented in runbook).

## Workflows

| Workflow | Trigger | Purpose |
|---|---|---|
| `orchestrator.yml` | `issues: [opened, labeled]` | Run the agent pipeline for a job |
| `qa-playwright.yml` | `deployment_status` | Run E2E against the new Vercel Preview |
| `repair-cycle.yml` | `workflow_dispatch` | Re-run repair + retest, called by Analyst |
| `factory-tests.yml` | `push, pull_request` | Vitest suite for the factory itself |
| `notify-telegram.yml` | reusable | Send a final message to the user |
| `ci-quality.yml` | `pull_request` | lint + typecheck + build gating PRs |
